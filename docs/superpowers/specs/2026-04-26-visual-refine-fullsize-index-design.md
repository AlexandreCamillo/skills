# Design Spec: Full-Size Mockup Index

## Problem

After the previous PR, the per-run index shows each component as a tiny scaled-down iframe (25% transform). To actually see what a variation looks like, the user has to click into the per-component composite and then back to the index. That extra click defeats the purpose of having a single navigable gallery — the user wants to scroll through the run and SEE the mockups, not see thumbnails of them.

## Goal

Make the index a full-size gallery: every component is rendered as a full block containing all `N` variations side-by-side (same composite layout that lives at `<component-id>.html`). The user can read every variation at native size by scrolling the index. The per-component composite file at `<component-id>.html` is preserved as a "more detail" deep-link that opens a dedicated page (same content, but isolated to one component for focused inspection or for citing in chat).

## Non-goals

- Removing per-component composite files. They stay; they are the canonical citation target (Copy-reference button writes their absolute path), and they are the link a user clicks for "more detail / open in own tab".
- Removing per-variation standalone files. They stay; they remain the iframe `src` for both the index and the composites.
- Lazy-loading optimizations beyond the existing `loading="lazy"` on iframes. The index of a 23-component, N=3 run has 69 iframes — Chrome handles this fine with lazy loading; no virtualization needed.
- A "compact mode" toggle in the index. The index is full-size; the compact view is the per-component composite page.
- A page-internal navigation sidebar (table of contents) for the index. The browser's built-in find-in-page is sufficient at this scale; if the run grows past ~50 components we can revisit.

## Behavior

```
+------------------------------------------------------------------+

|  Scroll to browse every component. Click "Open in dedicated      |
|  page" to focus one. Click "Copy reference" to cite a variation. |
+------------------------------------------------------------------+
|  ## topbar              [Open in dedicated page →]               |
|                         [Copy ref a] [Copy ref b] [Copy ref c]   |
|  Selected: b (Expressive) · score 26 · alts: a, c                |
|                                                                  |
|  +-----------------+ +-----------------+ +-----------------+    |
|  | A — Minimal     | | B — Expressive  | | C — Dense       |    |
|  | score 24/27 ok  | | score 26/27 ok  | | score 19 degr.  |    |

|  | <iframe ...     | | <iframe ...     | | <iframe ...     |    |
```

The grid inside each component block reflows with the same `grid-template-columns: repeat(auto-fit, minmax(420px, 1fr))` as the standalone composite — at narrow widths panels stack; at wide widths they sit side-by-side.

### File structure (unchanged from prior PR)

```

├── topbar.html                       # composite, single component, dedicated-page deep-link target

├── sidebar.html
├── sidebar/
│   ├── a.html
│   ├── b.html
│   └── c.html

```

No new files; no removed files. Only the index's content shape changes.

### Click flow

1. User opens index, scrolls; sees every variation of every component at native size.
2. User clicks "Open in dedicated page →" on `topbar` → opens `topbar.html` (the existing composite). That page shows ONLY the topbar's grid, with `← Index` link to come back.
3. User clicks Copy reference on a panel → clipboard receives `/abs/path/topbar.html#variation-b`. User pastes into chat.

## Risks and mitigations

- **The index becomes large at high N + many components.** With 23 components × 3 variations = 69 same-origin iframes, Chrome handles ~hundreds of lazy iframes routinely (e.g., social-media feeds). Mitigation: existing `loading="lazy"` on iframes; the user's natural scroll triggers loads as they go.
- **Duplication between index content and composite content.** The index's per-component block is intentionally the same DOM shape as the composite page. Mitigation: this is by design (so navigation is friction-free); the duplication is in the generated HTML, not in the SKILL.md, and the generator can share the same template internally.
- **User opens the index and gets confused why a single composite page exists.** Mitigation: the "Open in dedicated page" link is labelled to make the relationship obvious. The composite page is also the canonical citation target — the path the Copy-reference button writes — so it has a clear reason to exist beyond the index.
